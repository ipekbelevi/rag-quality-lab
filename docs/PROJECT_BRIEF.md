**Repository:** https://github.com/ipekbelevi/rag-quality-lab
**Author:** İpek Belevi (GitHub: ipekbelevi), QA engineer, AI sector
**Built:** October–November 2026, 8 phases, about $3.5 of API usage in total

---

## In one paragraph

Hello all. This is my hands-on study of how to test an LLM application. I built a small RAG customer-support chatbot for a made-up coffee company and tested it the way a QA engineer would: with a golden dataset I reviewed myself, with the DeepEval framework (GPT-4.1-mini as the judge model), with RAGAS as a second opinion on the same answers, with agent tests for tool calling, with Promptfoo red teaming mapped to the OWASP LLM Top 10, with bias and toxicity checks, with Langfuse tracing, and finally with a GitHub Actions quality gate that fails the build when quality drops. After every phase I wrote down what I did, what the numbers mean and what I learned.

## What it is and why it exists

LLM apps do not fail like normal software: the same question can get a different answer each time, the model can invent facts that sound right, and an attacker can hide instructions in a message. A classic `expected == actual` test catches none of this.

This project is a **complete, small-scale example of a quality process for an LLM app**: a chatbot plus every test layer around it, with real numbers. The company (Belevico) is fictional on purpose: the model has never seen its documents, so any invented detail is a visible hallucination.

## Headline results

| Experiment | What happened |
|---|---|
| Break the system on purpose (tiny chunks, deleted document, weak prompt) | The gate failed all three; the metric that dropped pointed at the broken layer |
| Same answers scored twice by the LLM judge | 5 of 130 pass/fail results flipped → the gate uses averages, not single items |
| Golden dataset generated by an LLM | ≈30% of items needed human correction; one reference answer was itself a hallucination |
| Broken tool description | Task completion barely moved (0.96 → 0.91), tool correctness fell to 0.27, tool calls +85%, latency +55% |
| Red teaming | Promptfoo reported 112/112 defended while the bot could still be used to scan order numbers; found by reading outputs, fixed with code limits, now 112/112 with 30 attacks blocked before any LLM call |
| Observability | The tracing tool first showed double the real token count; caught by cross-checking the app's own counter |

## What I learned, phase by phase (where I saw what)

| Phase | What I did | What I saw | The lesson |
|---|---|---|---|
| 0 Setup | Chatbot on Claude, judge on GPT, pinned versions, smoke test | Even a smoke test shows tokens and latency differ per provider | The system under test and the evaluator must be independent; versions must be pinned or scores drift without code changes |
| 1 RAG chatbot | 14 fictional docs, chunking, embeddings, tool-calling loop | Out-of-scope question → retrieval score 0.25 and the bot said "I don't know" | Testability is a design decision: `answer()` returns contexts, tool calls, tokens and latency, not just text |
| 2 Golden dataset | 29 items generated by an LLM, every one reviewed by hand | Wrong category on 1, invented rule in 1 reference answer, fake multi-hop items, missing trap type | The golden set is the test oracle; ≈30% of the generated draft needed a human. A wrong reference fails a correct bot |
| 3 Evals | DeepEval + RAGAS on the same answers, thresholds, 3 "break it" experiments | 14 red tests: some real (retrieval misses), some measurement errors (facts from the system prompt flagged as invented). Same answers scored twice: 5/130 flipped. RAGAS gives 0 to honest "I don't know" | Read every red test before believing it. Judges are noisy → gate on averages. Same metric name ≠ same metric |
| 4 Agent tests | Tool correctness (deterministic) + task completion (judge), 3 repeats | Broken tool description: task completion 0.96 → 0.91, tool correctness 1.00 → 0.27, +85% tool calls, +55% latency; in 2 cases the bot blamed the customer | Measure the process, not only the outcome. Don't use an LLM judge for what code can check |
| 5 Security | Promptfoo (OWASP LLM Top 10), bias/toxicity, 3 defense layers, before/after | Report said 112/112 defended; reading outputs showed order-number enumeration. Judge and deterministic check disagreed on repeating the attacker's code | A green security report proves nothing by itself. Prompts ask, code guarantees. Every defense needs a regression run (it cost +17% tokens) |
| 6 Observability | Langfuse traces, eval scores attached to traces | Tokens and cost showed 2× the real value (duplicate SDK spans); 90% of latency is in LLM calls | Observability data needs testing too; cross-check against an independent counter |
| 7 CI | Quality gate on every PR, weekly reliability run, same script locally and in CI | Local run: 3 gates pass in 5–6 min for ≈$0.40 | Build-breaking decisions belong to mean scores; per-item results are diagnostics. Cost is a design constraint |
| Security review | Dependency/secret audit, code-level fixes, documented accepted risks | 14 Python advisories, none exploitable here; one fix impossible due to a dependency conflict | A finding is closed by a fix, a compensating control, or a written accepted risk; never silently |

## Where these QA results are useful

- **Deciding whether an LLM change is safe to ship.** The gate pattern (golden set → judge → mean-score thresholds → build fails) is the same for any RAG or support bot; swap the documents and the thresholds.
- **Choosing and trusting an eval tool.** The DeepEval-vs-RAGAS comparison shows that scores are not portable across tools and that metric definitions must be read before a metric is adopted.
- **Building a golden dataset with GenAI, responsibly.** The generation + automatic checks + human review + versioned decisions flow is reusable; the 30% correction rate is a realistic planning number.
- **Testing agents and tool use.** The split into deterministic tool checks and judged task completion, plus pass^3 reliability, applies to any agent with tools.
- **Security sign-off for an LLM feature.** OWASP LLM Top 10 mapping, local-mode red teaming, deterministic security regressions and a defense-in-depth checklist with before/after numbers.
- **Budgeting.** Measured unit costs (an answer ≈ $0.0003, a judged item ≈ $0.0085, a gate run ≈ $0.40) and a scaling model for real datasets and live traffic (`docs/COST_REPORT.md`).
- **Production monitoring.** Traces with eval scores attached are the base for online evaluation: sample live conversations, judge them, alert on drops, feed bad cases back into the golden set.
- **Interviews and onboarding.** Every phase has a "how I would explain this" summary and concrete numbers; the repo works as a worked example for teams starting with LLM quality.

## Run it yourself (10 minutes)

```bash
python3.11 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env        # add your own Anthropic and OpenAI keys
.venv/bin/python -m app.ingest
.venv/bin/python -m app.chatbot "Where is my order BLV-482913?"
./scripts/ci_eval.sh        # the full quality gate, ≈ $0.40
```

No API keys are stored in the repository; everything runs on your own keys and account.

## Honest limits

Small datasets (30/12/13 items), a single cheap judge model, single-turn chat only, regex-based input filter, no ownership check on order lookups (documented, not fixed on purpose). All listed in the README and in `docs/SECURITY_REVIEW.md`.
