# Project overview in plain English

Hello all. This is my hands-on study of how to test an LLM application. I built a small RAG chatbot for a made-up company and then tested it the way a QA engineer would: with a golden dataset I reviewed myself, with the DeepEval framework (using GPT-4.1-mini as the judge model), with RAGAS as a second opinion on the same answers, with agent tests for tool calling, with Promptfoo red teaming mapped to the OWASP LLM Top 10, with bias and toxicity checks, with Langfuse tracing, and finally with a CI quality gate that fails the build when quality drops. After every phase I wrote down what I did, what the numbers mean and what I learned. The results are in the `README.md` and in the `results/` folder.

---

## What is this project for?

LLM apps do not fail like normal software. The same question can get a different answer every time. The model can invent facts that sound right. An attacker can hide instructions inside a message. A normal `assert answer == expected` test cannot catch any of this.

This project is a safe place to learn how to test these things. The company, **Belevico**, is fictional. The model has never seen its help-center documents, so every invented detail is easy to spot as a hallucination.

The goal is not a perfect chatbot. The goal is a **test setup that notices when the chatbot gets worse**.

## What was built

1. **A RAG chatbot.** It reads 14 help-center documents, finds the most relevant parts for a question, and asks Claude to answer using only those parts. It can also look up an order by order number with a small tool.
2. **A golden dataset.** 30 questions with reference answers, generated by an LLM and then checked by hand. It includes trick questions and questions with no answer in the documents.
3. **Evals.** Automated scores for faithfulness, relevancy, retrieval quality, hallucination and correct refusal.
4. **Agent tests.** Did the bot call the right tool, with the right parameters, and finish the task?
5. **Security tests.** Prompt injection, system prompt leakage, data disclosure, excessive agency, bias and toxicity. Then three layers of defense, measured before and after.
6. **Tracing.** Every request is recorded step by step: retrieval, LLM call, tool call, tokens, cost, time. Eval scores are attached to the trace.
7. **A quality gate in CI.** On every pull request the eval suite runs and the build fails when average scores fall below the thresholds.

## Frameworks and tools

| Tool | What I used it for |
|---|---|
| **Anthropic SDK (Claude Haiku 5.5)** | The chatbot itself, including tool calling |
| **OpenAI SDK (GPT-4.1-mini, text-embedding-3-small)** | Judge model, test-data generator and embeddings. A different model family than the chatbot, on purpose |
| **Chroma** | Local vector database for the documents |
| **DeepEval** | pytest-style LLM tests: faithfulness, answer relevancy, contextual precision and recall, hallucination, tool correctness, task completion, bias, toxicity, custom GEval criteria |
| **RAGAS** | A second set of RAG metrics on the same answers, to compare the two tools |
| **Promptfoo** | Red teaming: generates attacks per OWASP category and grades the answers |
| **Langfuse** | Tracing and observability; eval scores linked to traces |
| **pytest** | Runs the evals, the agent tests, the safety tests and the free unit tests |
| **GitHub Actions** | The quality gate on every pull request, plus a weekly reliability run |

## Test principles covered

These are classic testing ideas. The project shows what each one looks like when the system under test is an LLM.

- **Testing shows the presence of defects, not their absence.** The red-team tool reported 112 of 112 attacks blocked, but the bot still let an attacker scan order numbers. A green report is not proof.
- **The test oracle must be right.** The golden dataset is the oracle. About 30% of the LLM-generated draft needed human fixes. One reference answer contained an invented rule that would have failed a correct bot.
- **Independent testing.** The chatbot runs on Claude, the judge runs on GPT. A model should not grade its own family's work.
- **Non-determinism and flaky tests.** Scoring the same answers twice changed the pass/fail result of 5 out of 130 checks. So the gate uses average scores, not single items.
- **Threshold calibration.** Thresholds were not guessed. They come from the baseline scores minus the measured noise.
- **One variable at a time (controlled experiments).** The system was broken in three separate ways: tiny chunks, a deleted document, a weak prompt. Each time, the metric that dropped pointed at the broken layer.
- **Test the tests (mutation testing).** The tool-correctness metric was fed wrong inputs on purpose to confirm it goes red.
- **Measure the process, not only the result.** A broken tool description barely changed task completion, but tool calls rose 85% and latency 55%.
- **Exploratory testing turns into regression testing.** Problems found by red teaming became fixed, deterministic pytest cases.
- **Risk-based testing.** Security tests follow the OWASP LLM Top 10 list, not random ideas.
- **Defense in depth.** A prompt asks the model to behave; code guarantees it. Both layers exist and both were measured.
- **False positives matter too.** The input filter is tested against 42 real customer questions to make sure it does not block normal users.
- **Regression after every fix.** After adding defenses, the full RAG and agent suites were run again to confirm nothing else broke.
- **Shift left / quality gate.** The suite runs on every pull request, with production settings, and blocks the merge when scores drop.
- **Observability as a test subject.** The tracing tool first reported double the real token count. It was found by cross-checking with the app's own counter.
- **Human in the loop.** Generated test data, red-team outputs and judge reasons were all read by a person before being trusted.
- **Cost is a quality attribute.** Every phase has a cost estimate. The defenses added 17% more input tokens; this is reported, not hidden.

## What I learned, in one sentence each

- Every red test is not a bug; some are measurement errors.
- An LLM judge is a useful but noisy instrument.
- The same metric name means different things in different tools.
- Prompts can be bypassed; code limits cannot.
- Fictional data makes hallucinations visible.
- Write down why a threshold, a version or a design choice was chosen.

## How to read the repository

Start with `README.md` for the architecture and the result tables. The `data/` folder holds the documents and all test cases. The `evals/` folder holds the tests and the gate. The `results/` folder holds every saved run. The `scripts/ci_eval.sh` file is exactly what CI runs.
